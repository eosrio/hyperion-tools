Hyperion 4.5 · Architecture vision

One stack serves every Antelope API shape. Each datum stored once.

A Hyperion operator already runs nodeos, Elasticsearch, and, since 4.0, MongoDB. Hyperion 4.5 makes that same infrastructure answer Hyperion v2 history, the Light API, AtomicAssets, and native chain v1 reads. No second database per app. No datum stored twice. State stays in the state tier. History stays in search. One SHiP feed keeps them current.

03 — State tier

One file, many namespaces.

The state tier is a single memory-mapped .wseg. It stays live at chain head and compacts in place. Another API is another namespace, not another database.

Layout

Namespaced tables in one .wseg

A columnar file, memory-mapped. The table-id space is partitioned so several API domains share one reader.

  • 0–10 Light API state Proven
  • 11–21 AtomicAssets state Proven
  • reserved Chain v1 / generic tables Planned
  • reserved AtomicMarket Planned

Forward store keyed by id, plus per-dimension inverted posting lists — owner, collection, schema, template, and data facet — and presorted orderings. Hybrid roaring postings. Served embedded, with no IPC. Each datum once.

Runtime

Live, then compacted in place

Reads merge a frozen base with a freshness overlay. Readers keep serving through the swap.

  1. Frozen base

    Immutable, mmap'd, and read by binary search.

  2. Freshness overlay

    The SHiP feed applies mint, transfer, burn, and setdata. Reads merge the base and the overlay. The forward record is the sole arbiter, so stale postings are harmless.

  3. Two-phase apply

    Base reads stay lock-free. A brief in-RAM commit holds the freshness lag to hundreds of µs, and readers are never stalled.

  4. Compaction

    Fold the base and the overlay into a fresh segment in the background, then an atomic ArcSwap hot-swap. Overlay RAM is reclaimed. Readers keep serving.

04 — Evidence

Measured on WAX mainnet.

These figures are the AtomicAssets state tier, the richest query surface, measured end to end. The mechanism under them is domain-generic.

The store

21 GB

232M live assets on disk. Under Mongo at 24.3 GB, and under the incumbent Postgres stack at about 692 GB.

sub-µs

Point, facet, and collection page-1, from embedded mmap. 150k–887k requests/s on one thread.

38 min

Snapshot to fully indexed. 0 decode errors. 200/200 parity with the live API.

~28×

Less storage than eosio-contract-api. No burned rows, and no history kept in the state tier.

Live serving from chain head

370k/s

Mutations applied on one thread. About 37× a SHiP burst.

~276 µs

Commit hold at p50. Reads stay sub-µs with the overlay active.

557k req/s

Readers served while a writer ingested. Reader p50 about 1 µs.

0 stale

Page-merge invariant held across 38,974 page entries at scale.

Compaction and hot-swap

6.4 min

Fold of the 232M base plus overlay into a fresh segment. About 3× faster than the original build, because the fold reads mmap rather than a database stream.

0 / 60k

Fold equivalence. The new base alone answers identically: 0 mismatches across 60,000 checks.

396 → 0 MB

Overlay heap freed on swap. What remains is evictable page cache.

3.68M req/s

Daemon readers stay lock-free across hot-swaps. A reader stall is a brief per-swap tail-replay. The fold itself does not stall readers.

All of the above is the AtomicAssets instance of a domain-generic mechanism: an immutable base, a freshness overlay, and ArcSwap compaction. The same machinery hosts the Light API overlay and chain v1 tables in the same segment. That generalization is the remaining 4.5 integration work.

05 — Roadmap

What closes the loop.

The decoder, the store, the overlay, and compaction are measured. What remains is one segment, one applier, and one gateway for every shape.

Proven In this repo

  • atomicdata decoder. Byte-exact across 77/77 live schemas, with 200/200 parity.
  • snapshot-load presets. AtomicAssets, AtomicMarket, and Light API shapes.
  • AtomicAssets WormDB store. 21 GB, with sub-µs faceted reads.
  • Live freshness overlay. Chain head is applied, and reads stay sub-µs.
  • Compaction daemon. ArcSwap hot-swap, running continuously.

Planned The 4.5 target

  • One segment, both namespaces. Light API and AtomicAssets in the same .wseg.
  • One applier. Both contract domains leave the shared SHiP feed through one router.
  • Light API overlay. The live overlay extended to token and permission deltas.
  • Deep pages and AtomicMarket. Cursor pagination, AtomicMarket, and range indexes.
  • One HTTP gateway. All four API shapes served from the same store.

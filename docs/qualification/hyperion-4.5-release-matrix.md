# Hyperion 4.5 release qualification matrix

Status: draft for [release-scope issue #20](https://github.com/eosrio/hyperion-tools/issues/20). The operator selected **v4.1.0, v4.0.8 and v3.3.10-1** as 4.5 upgrade sources and **both Elasticsearch 8.x and 9.x retained-history lanes** on 2026-10-23. For the 3.3.10-1 path, the no-full-history-reindex commitment covers **7.x-created indices**; pre-7-created indices need a separate migration and are outside this supported matrix. Exact source-server configurations and acceptance evidence remain to establish; a test row is not a passing support claim. The companion [primary-source research](hyperion-4.5-matrix-research.md) records the observed pins and upgrade constraints.

The [architecture definition](../architecture/hyperion-4.5.md), [upgrade decision](../adr/0040-preserve-history-without-full-reindex-on-45-upgrade.md), and [roadmap](../roadmap/hyperion-4.5.md) govern every row below. In particular, a supported upgrade keeps Elasticsearch history queryable and resumes indexing without a full history reindex. New or changed state projections initialize separately. The matrix is a finite set of release gates, not the Cartesian product of every chain, endpoint, topology, backend and runtime.

The selected target server lanes are **Elasticsearch 8.19.23** for retained 8.x history and a compatible 3.3-era 7.x-created-index path, and **Elasticsearch 9.5.5** for retained 9.x history and a separately qualified 8.x-created-index upgrade. Each lane pins an exact build/image digest at execution and proves the actual old indices remain queryable while new writes continue. These are the first exact qualification targets, not a claim that every 8.x or 9.x patch behaves identically. Inventory deployed server and index-creation versions before publishing the supported patch range.

The U1/U2/E8 first fixtures keep the Elasticsearch server constant while changing Hyperion. Separate server-compatibility rows exercise a qualified **8.19.23** landing and the candidate **9.5.5** path with retained indices, after recording their creation versions and checking [Elastic's upgrade requirements](https://www.elastic.co/docs/deploy-manage/upgrade/prepare-to-upgrade). Elasticsearch 8.x provides [full query and write support for 7.x-created indices](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/setup-upgrade.html). Indices created before Elasticsearch 8 require an explicit archive or migration decision before a 9.x server upgrade; they cannot silently be counted as retained writable 9.x history. This allows an 8.x release lane for compatible 3.3-era history without changing the no-full-history-reindex requirement. The test and benchmark harnesses select 9.5.5, but that default does not prove retained-index compatibility or mandate a production server upgrade. The [9.5.5 research](../research/elasticsearch-9.5.5.md) and [History API #198](https://github.com/eosrio/hyperion-history-api/issues/198) own its separate request, bulk, replica, pressure and resource qualification.

The target configuration records a single-node/zero-replica deterministic fixture and a representative multi-shard/replica configuration. Preserve original templates, mappings, index sort, partition names, aliases, `settings.index_version`, replica count and retained source documents. Never create a fresh 4.5 index in place of the source history and call the upgrade qualified.

Use **one active state backend per chain** across state API domains. MongoDB is mandatory for launch. ## Existing state API compatibility inventory

Retained history checks must not hide state API regressions. The [existing MongoDB baseline](../architecture/hyperion-4.5-existing-mongodb.md) identifies configured contract tables, sync, live reload, ABI lookup, live writes and `/v2/state/get_table_rows`. Its published route accepts `contract`, `table`, scope and metadata selectors, `primary_key`, a JSON `filters` object with Mongo-shaped comparison operators, `sort_by`, `sort_direction`, `skip`, `limit`, and `rows_count`. The pre-upgrade oracle must capture representative successful and failing requests, metadata, count and ordering. Preserve the public behavior on MongoDB; if a portable query contract cannot express a case, decide and document its migration explicitly before offering another backend. Do not expose native database queries through plugin definitions.

The published 4.1.0 source also has Mongo-backed `get_proposals`, `get_tokens`, `get_top_holders` and `get_voters` routes. Capture their selector, count and response behavior. Inventory the remaining state and stats families (`get_account`, links, key accounts and usage/count routes) to determine their actual backing store and whether each is preserved, intentionally changed with a client migration, or unavailable because its optional feature is disabled. `/v1/chain/get_table_rows` is a distinct chain-RPC proxy and must not be mistaken for the indexed-state route. The full AtomicAssets/AtomicMarket plugin adds its own required API domain and parity oracle.

## Fixture manifest and exit rule

Each run writes a machine-readable manifest with source and target commits/tags, dependency locks, chain ID and bounded input range, Elasticsearch server/build/image digest and index creation versions, original index settings/mappings/aliases/counts, MongoDB/adapter versions, configuration including `index_version`, plugin/SDK pins, commands, result digests and cleanup/retention location. Record pre-upgrade and post-upgrade query outputs plus the first newly indexed block/action after restart. Keep component or synthetic test success separate from full-worker and live-chain evidence.

Issue #20 is complete when exact source-server configurations are selected, this matrix is approved, the first #190 fixture is specified reproducibly, and remaining public API migration decisions are explicitly owned. Passing any row remains a separate implementation or release-qualification result; do not close an unchecked gate based on this plan.
